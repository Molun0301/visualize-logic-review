# 各类图的画法、审查模板与代表性测试

目录：通用约定 · 各类图的语义与画法 · 审查结果模板 · 代表性测试 · 交付前检查

## 通用约定

1. 标题写明“现状 / 提案 / 对比”和主题；`question` 写本图回答的问题；`basis` 写证据范围、版本和是否运行过。
2. 先在图上设默认 `status`，只给例外元素单独标。假设写成可验证的陈述；未知要给出补证方式，不替用户编造业务决定。
3. 关键节点和关键连线挂证据编号。区分“源码里存在这个分支”和“运行时观察到这个行为”。
4. 每条失败、超时、取消、重试路径都要有终点或责任方；不适用就不画，没有定义就标未知。
5. 一屏读完：5–12 个节点；大模块折叠成一个节点，局部图沿用相同编号。颜色之外还有线型和文字区分，不只靠红绿表达含义。
6. 对比现状与提案时，优先画两张同编号的图；只在一张图里对比时，用 `status`（fact 与 proposal）区分新旧部分。

## 各类图的语义与画法

### 控制流程图（flowchart）

- 一个 `start`，所有出口用 `end` 并以 `tone` 区分成功和失败。
- 主路径连线用 `main`，让它从上到下连成一条；失败分支用 `error` 走向失败出口。
- 每个判断的出边写条件，条件互斥并覆盖全部情况（例如“成功 / 明确失败 / 超时”三条）。
- 循环画出回边（`retry`）和退出边，回边标签写上限或预算。
- 只是业务流程时叫“控制流程图”；只有映射到基本块和控制转移时才叫 CFG。

### 时序图（sequence）

- 区分同步调用、异步消息和返回；失败返回用 `tone: error`。
- 用 `alt` 画互斥分支，`opt` 画可选步骤，`loop` 画循环（标签写终止条件），`par` 画并行。
- 用注释（note）标出等待点、超时时长、锁的持有范围。
- 标清超时由谁计时、谁负责取消、迟到的结果如何处理。不要把“界面停止等待”画成“后台副作用已停止”。
- 上下顺序只是设计中的顺序，不能证明跨线程的先后关系。

### 状态机（state）

- 用 `initial` 和 `final` 画初态和终态；失败、取消状态要画出来。
- 迁移标签写“事件 [守卫] / 动作”。同一状态同一事件有多条迁移时，守卫要互斥。
- 业务状态和执行任务的状态分开画。
- 写明迟到事件、重复事件和非法迁移的处理方式；未定义的迁移标 `unknown`。

### 架构图（architecture）

- 一张图只选一个 C4 层级（系统上下文、容器、组件），不混层；简化框图写“C4 风格概览”。
- 用 `groups` 框出进程、网络、部署单元和信任边界（`style: trust`）；外部系统用 `external` 形状或 `style: external` 分组。
- 连线写协议或接口（HTTPS、gRPC、事件名），箭头表示依赖或调用方向。
- 静态架构不能证明运行时行为。

### 数据流图（dfd）

- 区分外部实体（`external`）、处理（`process`）和存储（`store`）；箭头代表数据，不代表控制顺序。
- 每条连线写数据名称；标出复制、共享、删除和保留期，没有证据时写未知。
- 用信任边界分组标出敏感数据跨越边界的位置。

### 调用图（call）

- 静态调用图只表示“可能调用”，动态调用图只覆盖采集到的运行。
- 标出入口、递归和跨模块副作用；反射、插件、回调和动态分派无法解析时标 `unknown`。
- 局部调用关系不能推出全局没有死锁。

## 审查结果模板

先展示图，再按需给出下面各项，不必每项都写：

- 结论：推荐的方案和最重要的一个理由
- 范围：图覆盖了什么；现状还是提案；依据了哪些输入和版本
- 关键路径：正常路径，以及最重要的失败或并发路径
- 发现：级别、位置（锚点）、触发条件、影响、证据、建议和代价
- 验证：测试编号、覆盖的连线或状态、输入或调度方式、预期结果、运行状态
- 决策：只列真正影响产品行为或需要授权的选择；没有就写“无新增决策点”，并继续已授权的实现
- 限制：没看到的代码、没解析的动态调用、没测的运行时顺序等具体盲区

## 代表性测试

- 分支：关键条件的真和假、边界值、校验失败和异常传播
- 循环与重试：零次、一次、达到上限、持续失败、退避等待中被取消
- 并发：重复触发、交错完成、取消与成功竞态、超时后迟到的回调、锁顺序、没有悬挂任务
- 副作用：重复请求不会重复写入或扣款；失败后的补偿有证据；无法补偿时不虚构回滚
- 生命周期：成功、失败、取消都释放资源；缓存失效正确；敏感信息不进入日志
- 状态：所有合法迁移可达，终态稳定，非法迁移按定义拒绝或记录

预期结果要可验证。例如“第 3 次重试仍失败后进入 FAILED，关闭连接，不再排队”，而不是“测试异常情况”。

## 交付前检查

1. 渲染没有错误；每条结构警告都已处理，或写进 limitations 说明原因。
2. 用 `snapshot.py` 截图后实际看过 PNG：文字没有被裁切或遮挡，箭头方向正确，主路径一眼可见。没看过就如实说明视觉检查未完成。
3. 每条发现都锚定到图上元素；`confirmed` 级别有证据。
4. 输出写到任务自己的目录，不写进技能目录或业务源码目录；通过宿主支持的附件或链接交付 HTML，CLI 环境给出真实的绝对路径。
